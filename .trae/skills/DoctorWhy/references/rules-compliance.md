# 暗规则库 · 数据与合规(Data & Compliance)

> 医疗数据(患者健康信息)的采集、存储、访问、审计规则。通用 AI 按普通 SaaS 习惯做,不知道医疗数据有多敏感。
> 每条 = 规则 + 为什么(法规/现实)+ 踩过什么坑。
> 涉及隐私、监管,违规代价高(罚款、吊销、诉讼)。审查时逐条过,追问时按需带出。

## 标准来源

本库规则依据以下法规/标准,审查或核对时查对应章节:

- **国内《个人信息保护法》(PIPL)** —— 个人信息最小必要、处理告知同意、删除权(第 19、47 条)。
- **HIPAA Privacy Rule**(45 CFR 164)—— 受保护健康信息(PHI)的使用与披露、最小必要(§164.502/514)。
- **HIPAA Security Rule**(45 CFR 164.308-314)—— 访问控制、审计、加密、传输安全。
- **《网络安全法》/《数据安全法》** —— 数据分类分级、重要数据保护。
- **GB/T 35273**(个人信息安全规范)—— 脱敏、最小化、日志留存。

> 每条规则的具体条文位置,以上述法规/标准的对应章节为核对依据;单条概括与标准原文冲突时,以标准原文为准。


---

## 1. 识别"受保护健康信息"(PHI),默认最小暴露

- **规则**:患者姓名、病历号、身份证、检验号、样本号、检查图像、日期(与患者相关时)都是 PHI。默认不展示、不传日志、不做 UI 默认字段;能脱敏就脱敏。
- **为什么**:国内《个人信息保护法》/HIPAA 都要求"最小必要"。一张骨髓片图像 + 样本号即可定位到具体患者。
- **踩坑**:把患者姓名当普通字段做进列表、日志、接口响应;图床/云盘直接传带 ID 的检查图像。

## 2. 日志禁止记录患者名 / 病历号 / 样本号

- **规则**:日志只记可脱敏标识(如内部 UUID 或脱敏后的短码),禁止写姓名、完整病历号、身份证号。日志里的 ID 与真实患者可分离存储。
- **为什么**:日志最容易泄露——会被运维、调试、第三方拿到,且常被忽视。写进日志 = 变相公开。
- **踩坑**:打日志时顺手把"用户张三 病历号 2025001"写进去;异常堆栈里带样本号,报错上传后泄露。

## 3. 审计追踪:谁在何时看了谁的记录

- **规则**:所有对患者数据的访问/修改/删除,必须有不可篡改的审计记录(操作者、时间、对象、动作、前后值)。只读查看也要留痕。
- **为什么**:医疗记录是法律证据,监管要求可追溯"谁在何时看过什么"。没有审计,纠纷时无法自证,违规时无法追责。
- **踩坑**:普通 SaaS 只记"用户增删改",不记"谁查看了某患者";或审计日志可被普通用户删改。

## 4. 访问控制:角色分级,默认最小权限

- **规则**:按角色分级(管理员/技师/医生/只读),默认最小权限;未授权角色看不到其他患者数据。医生/技师/患者数据隔离。
- **为什么**:医生只看自己科室、技师只看自己在跑的样本;越权查看是隐私违规。角色分级是医疗系统基础。
- **踩坑**:所有登录用户一个权限,任何登录者能查全库患者;或密码管理弱(默认密码、无过期)。

## 5. 传输与存储加密

- **规则**:患者数据传输用 TLS/HTTPS,存储敏感字段加密;检查图像静态加密。禁止明文传/存 PHI。
- **为什么**:PHI 在传输/存储中被截获 = 泄露。加密是合规硬要求,也防内部越权直接读库。
- **踩坑**:设备直传云盘无加密;数据库明文存身份证;接口 http 明文传病历。

## 6. 数据存储边界:本地优先,控制外传

- **规则**:医疗设备数据默认存本地/院内,上传到外部(云盘/第三方)需显式授权 + 审计。检查图像优先本地存储,不默认传公有云。
- **为什么**:医疗数据跨边界外传是高风险动作,尤其图像(可识别患者)。院内设备直连公有云是常见违规。
- **踩坑**:检查图像"为了省事"直传百度网盘/阿里云,无加密无审计;或软件默认把样本数据同步到厂商服务器。

## 7. 删除与保留:患者数据的生命周期

- **规则**:明确数据保留期与删除策略;患者请求删除/撤销同意时,系统能真正删除(含备份、缓存、日志关联)。不允许永久堆积。
- **为什么**:法规赋予患者"删除权/撤回同意权",系统必须能响应,否则违规。
- **踩坑**:删了主表但备份、日志、缓存里还残留;或根本没有删除功能。

## 8. 导出/打印需二次确认 + 留痕

- **规则**:导出/打印患者报告、批量下载图像,需显式确认,并记审计;大范围导出要审批。
- **为什么**:批量导出是数据外泄的主要通道。一键全量导出患者库 = 数据带走。
- **踩坑**:报告页面一个"导出 Excel"按钮直接导出全库;导出无任何记录。

## 9. 脱敏是默认,不是可选项

- **规则**:UI、报告、接口、测试数据里,默认脱敏(姓名→张*,病历号→尾号,图像去标识)。只有授权场景才显示完整。
- **为什么**:脱敏是"最小必要"的落地方式;演示/培训/第三方接口尤其要脱敏。
- **踩坑**:给合作方做接口时把完整病历直接给出去;截图演示软件时患者信息全裸奔。

## 10. 数据与模型分开,训练数据合规

- **规则**:患者数据用于训练 AI 模型需授权/脱敏;模型产出的分类结果(如"40分类细胞计数")与患者记录关联存储需合规留痕。
- **为什么**:用真实患者数据训练是敏感行为;AI 诊断结果写入医疗记录需可溯源(哪个模型、哪个版本、谁复核)。
- **踩坑**:拿医院真实片子直接训练模型不脱敏;AI 出的报告无版本/无复核人,出问题无法追责。

## 这些规则能点破什么矛盾(供"点破隐含矛盾"动作使用)

- 用户说"扫描日志里顺便记一下玻片对应哪个患者,方便排查" → 点破"排查方便" 与 "日志禁止患者信息" 的矛盾:用脱敏短码代替。
- 用户说"患者记录直接存云端,省服务器钱" → 点破"省成本" 与 "存储边界/加密" 的矛盾:默认本地,外传需授权+审计。
- 用户说"所有登录用户都能看全部玻片记录" → 点破"简单" 与 "角色分级/最小权限" 的矛盾:医生只看自己科室。
- 用户说"AI 分类结果直接出报告给医生" → 点破"省人工" 与 "结果可溯源/需复核" 的矛盾:AI 报告要有版本和复核人。
